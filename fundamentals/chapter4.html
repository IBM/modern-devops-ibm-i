4. Source management with Git

Git plays a central role in modern IBM i development because it provides a single, authoritative repository for all human-authored source artifacts. Traditional IBM i development often relied on source stored in multiple locations, with individual developers maintaining their own compile processes or relying on undocumented tribal knowledge to promote changes.

By consolidating all source into a version-controlled repository, Git eliminates ambiguity regarding which version of the source is current, who changed what, and how changes should be integrated. Git's full historical record, combined with structured collaboration methods such as pull requests, provides transparency and traceability that manual methods cannot reproduce.

In the IBM i context, Git does not replace the existing object and library model but complements it by clearly separating the intent of developers from the compiled output executed on the system. Source files (RPG, COBOL, CL, SQL, DDS/DDL), shell scripts, Makefiles, and other human-generated assets belong in Git. Compiled objects, produced by the system from those source files, belong in runtime libraries. This distinction ensures that libraries retain their proper role as deployment locations rather than being used interchangeably for development work. Establishing this separation strengthens consistency across environments and makes it possible to reproduce builds reliably.

A key enabler of this separation is the introduction of build scripts. Before implementing pipelines or advanced automation, teams must capture the exact steps needed to transform source into runtime objects. A build script serves as a stable definition of how an application is compiled, which libraries are used, what parameters are required, and how the resulting objects should be packaged or deployed. Even a simple script that compiles a single module is sufficient to begin establishing consistency. Over time, this script becomes the foundation for automated processes, ensuring that all developers and tools use the same build logic, independent of personal habits or environment variations.

Effective source management also requires that all supporting artifacts — not only source code — be versioned in Git. Library lists, compile settings, testing utilities, SQL migration files, configuration parameters, and deployment metadata should all be stored alongside the application's code. This creates a unified, reproducible definition of the application and its environment. The result is a development process where every element needed to rebuild the application is captured in version control rather than scattered across personal notes or individual workstations.

Branching strategies should remain intentionally simple. Given that IBM i applications often have tightly coupled components and frequent deployment cycles, a model built around a stable main branch and short-lived feature branches typically offers the best balance of flexibility and control. This approach reduces process overhead while still supporting structured reviews and controlled integration.

Treating runtime libraries strictly as the output of the build process is equally important. Manual changes to objects in runtime libraries introduce drift, undermine reproducibility, and create uncertainty when investigating production issues. Ensuring that all runtime objects originate from Git through a defined build process eliminates these risks and reinforces the integrity of the deployment workflow.

Together, these practices form the source management backbone of a modern IBM i development environment. They connect directly to the themes explored earlier in this series: the architectural clarity of IBM i, the modernization of development techniques, and the adoption of modern DevOps principles focused on consistency and visibility. With source defined in Git, build steps documented in scripts, and deployment libraries treated strictly as runtime destinations, teams gain a reliable and repeatable foundation from which automated testing, approvals, and CI/CD pipelines can be introduced with significantly reduced risk.

Why Git on IBM i?

  • Single source of truth, full history, easy collaboration and rollback
  • Works with pull requests and code review so knowledge isn't trapped in inboxes
  • Integrates directly with CI/CD tools when you're ready

Mapping IBM i to Git

  • Git repo: where source lives (RPG, COBOL, CL, SQL, scripts)
  • Compile: transforms source into objects placed in libraries (runtime)
  • Pipeline: the "robot" that runs your compile and promotions the same way every time

Practical starter rules

  • Put all application source in Git, including CL, SQL, DDS/DDL, and build scripts
  • Use a simple branching model (e.g., main + feature/ branches) to start
  • Add a build script that compiles from source to a dedicated build library — make that the single path to runtime objects
  • Keep environment config (library lists, target libs) in versioned scripts so you can reproduce builds later
Tip

Your first "automation" can be a single shell or Makefile that builds one module. Pipelines come next, using the same script.
