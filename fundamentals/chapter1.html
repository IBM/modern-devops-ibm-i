1. DevOps 101

In the IBM i context, DevOps is fundamentally about visibility and repeatability. Every change is tracked in Git, and builds are executed the same way every time through scripts or pipelines, eliminating the guesswork of manual steps.

This approach encourages small, safe changes that are easier to validate and roll back when necessary. It also supports true separation of duties through automation with approvals and controls embedded in the pipeline itself, making them auditable and consistent instead of relying on ad hoc emails or chat messages.

What DevOps really means here

  • Visibility and repeatability: Track every change (Git), build the same way every time (scripts/pipelines).
  • Small, safe changes: Fewer surprises, easier rollbacks.
  • Separation of duties with automation: Approvals happen inside the pipeline (auditable), not in emails or chats.

Common fears and how to address them

Teams often have concerns when adopting modern DevOps, but each one has a practical path forward.

"We'll break something." Start with one app, one pipeline. Keep promotions automated but gated; add tests over time.

"We don't have time to learn all this." You don't need everything at once. A simple sequence — Git first, then automated builds, then tests, then deployment — keeps progress manageable.

"Our processes already work." Modern DevOps doesn't replace good processes, it captures them, so they become consistent, faster, and easier to recover when issues occur.

Minimum viable pipeline

A minimum viable pipeline on IBM i follows a straightforward path: developers commit code to Git, an automated process compiles the application into a dedicated build library, basic tests run (such as RPGUnit or SQL-based checks), an approval step provides oversight, and then the pipeline promotes objects to test or production environments automatically.

  1. Commit to Git
  2. Automated compile to a build library
  3. Basic tests (RPGUnit / SQL checks)
  4. Approval
  5. Automated promotion to TEST/PROD
Key Insight

The specific tooling — whether Jenkins, GitHub Actions, GitLab CI, or Azure DevOps — is flexible. What matters most is choosing a platform your team can support, because consistency matters more than the brand behind the pipeline.
