4. The Integrated File System (IFS)

The Integrated File System (IFS) plays a central operational role in modern IBM i development, particularly as organizations adopt DevOps practices and open-source tooling. Unlike the traditional QSYS.LIB environment used for storing and managing compiled IBM i objects, the IFS provides a POSIX-style filesystem that behaves similarly to those found on Linux, UNIX, and macOS systems.

This capability significantly broadens what developers can do on IBM i by enabling direct use of open-source utilities, language runtimes, shell scripts, and cross-platform tools that expect a standards-based file structure.

Because the IFS supports ordinary text files, it becomes the natural home for the wide range of artifacts used in today's DevOps workflows. YAML and JSON configuration files, pipeline definitions, testing frameworks, formatting tools, source linters, and shell-based build automation can all run directly against IFS-hosted content. This flexibility also improves interoperability. CI/CD platforms, distributed version control systems, and open-source build tools can exchange files with the IFS just as they would with any other standards-based filesystem. As a result, IBM i can participate seamlessly in multiplatform automation pipelines without requiring custom adapters or proprietary workflows.

Modern IBM i development environments, particularly those based on VS Code, SSH workflows, or remote editing tools, typically use the IFS as their staging area. Developers retrieve source from Git into the IFS or synchronize workstation files directly to IFS paths where scripts, compilation steps, and automated processes can access them. The resulting compiled objects, however, do not remain in the IFS — they are placed into IBM i libraries, which continue to serve as the system's authoritative runtime containers. This arrangement reinforces a clean separation between development artifacts and production objects: the IFS holds source, scripts, and configuration, while libraries store the executable objects that the IBM i runtime uses.

A consistent and reliable DevOps pattern emerges from this separation. Source code is pulled from Git into an IFS workspace, where build scripts execute predictable compile commands that generate modules, service programs, and other runtime objects into a controlled build library. From there, the deployment process promotes those objects through test and production environments using automated controls and approvals. This workflow isolates the "source world," where developers and tools manipulate text files in the IFS, from the "runtime world," where libraries hold compiled artifacts. The distinction simplifies troubleshooting by enabling teams to verify exactly which source produced a given object, and it reduces rollback risk by ensuring that runtime environments can be restored from version-controlled source and scripted builds rather than manually edited objects.

By providing a familiar filesystem model and serving as a reliable bridge between open-source tooling and IBM i's object-based runtime, the IFS has become a cornerstone of modern DevOps practices on the platform. It allows IBM i to integrate cleanly with contemporary development ecosystems while preserving the strengths of the underlying architecture. In this way, the IFS is not merely a compatibility feature — it is an essential enabler of modern, automated, and maintainable delivery pipelines.

Why the IFS matters for DevOps

The IFS gives IBM i a familiar POSIX-style filesystem, which makes it easier to:

  • Work with open-source tools (linters, formatters, test runners)
  • Store and manipulate text files (YAML, JSON, scripts, pipeline config)
  • Exchange artifacts with non-IBM i systems during CI/CD

Many modern IBM i workflows (e.g., VS Code + SSH, scriptable builds) naturally use the IFS as the staging area while compiled objects still land in libraries.

A simple, safe pattern

  1. Pull source from Git into the IFS (or your workstation syncs to the IFS)
  2. Run build scripts that compile from the IFS into a build library
  3. Promote the built objects through TEST → PROD with automated steps and approvals
Key Insight

This cleanly separates "source world" (IFS) from "runtime world" (libraries), which simplifies troubleshooting and rollback.
