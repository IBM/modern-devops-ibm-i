Getting started: your first 30–60 days

The early stages of modernizing IBM i development benefit from a focused, time-boxed approach. The goal for the first 30–60 days is to establish version control, define a consistent build process, introduce basic automation, and begin shaping the application into a structure that supports safer, incremental change.

First 30–60 days

Weeks 1–2: Put one app's entire source into Git; add a readme describing how you compile today.

Weeks 3–4: Create a single build script (CL/PASE/Make), no pipeline yet. Compile consistently to a build library.

Weeks 5–6: Wrap that script in a pipeline (Jenkins, GitHub Actions, GitLab, or Azure DevOps). Add a basic approval step and promote to TEST automatically.

Weeks 7–8: Add basic tests (RPGUnit or SQL checks). Start extracting one function into a service program.

Pitfalls to avoid

  • Starting with UI refacing before modularizing the core; it looks good but doesn't reduce risk
  • Pushing all tools at once; adopt in the order your team can absorb
  • Letting manual promotions linger; the longer they coexist with automation, the more drift you'll see

What success looks like

  • You can answer, "What changed? Who changed it? How did it get to PROD?" in seconds, because Git and your pipeline tell you
  • Builds are repeatable and auditable
  • Small changes feel safe, and new developers get productive quickly with familiar tools
Key Insight

Modern DevOps captures your proven steps so they become consistent, fast, and recoverable. The goal isn't perfection from day one — it's a reliable foundation you can build on.
